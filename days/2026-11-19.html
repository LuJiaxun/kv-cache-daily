一、重点方向：混合注意力下的非前缀复用（5 篇）

1. LatentRemedy: Efficient Remedy For Non-Prefix KV Cache Reuse in Multi-Agent Systems

  • 链接：https://arxiv.org/abs/2610.18014
  • 时间：2026-10-13
  • 方向：非前缀复用 · 语义污染 · 任务条件化补救

摘要：多 agent 系统共享同一批上下文块，非前缀复用能显著提效；但当 agent 任务相互冲突时，直接复用别处的非前缀 KV 会让性能最多掉 90%。现有补救（选择性重算、基于偏移的校准）只能挽回一小部分损失。论文指出问题不只在于 KV 表示被“污染”，还在于目标 agent 难以在自己的指令下解读被复用的上下文。LatentRemedy 因此用少量任务条件化的 latent token 来帮目标 agent 使用共享上下文而不必重算整块：用一个 MLP 把目标前缀的最后隐状态映射成几个 latent token，插在被复用的 KV 块之后与共享上下文交互，并通过 full-prefill 蒸馏训练该 MLP。在冲突任务上一致优于现有复用基线，且随着缓存变大 TTFT 仍接近“直接复用”。

对广域的启示：这是对“跨域复用不是免费的”最直接的量化。跨域搬来的 KV 若来自不同任务/不同 agent，语义会漂移；此时传几个 latent token 让接收端自行校准，比多传几 MB 的 KV 或整段重算都便宜。这份补救信息只有几个 token 的大小，跨网成本几乎可以忽略。

2. CacheWeave: Learning to Recompute for Efficient Position-Independent KV Caching

  • 链接：https://arxiv.org/abs/2611.01735
  • 时间：2026-11-01
  • 方向：位置无关缓存 · 学习式块选择 · 混合注意力

摘要：位置无关缓存（PIC）跨位置、跨请求复用 chunk KV，但独立编码会丢掉 chunk 之间的交互，精度下降。论文实测发现：PIC 训练与基于规则的重算，单独或组合都不能稳定恢复到全量 prefill 的精度；而在 PIC 训练过的模型上做“oracle 指导的重算”，同样预算下精度有明显提升——说明关键在选对要重算的块。CacheWeave 先把整个 backbone 适配到 PIC，再冻结它，用适配模型的 oracle 训练一个模型原生的块选择器；选择器只用紧凑的 chunk 特征与 question 隐状态，不需要抽取 backbone 的注意力分数，且选择的是与 KV 块对齐的连续 token 块，从而既高效又限制 copy-on-write 放大。运行时 CacheWeave-Serve 支持私有与共享 KV 缓存，选择与重算都在 GPU 上，并为混合注意力模型的滑动窗口 KV 做 staging。三个模型四个任务上，5% 重算预算下比 CacheBlend、ProphetKV 平均高 7.2 与 3.5 个百分点，相对全量 prefill 平均精度损失 1.6%；32-token 块下单请求 TTFT 最高快 16.1×（相对全量 prefill）、1.7×（相对 ProphetKV），负载下 SLO goodput 最高 7.8×。

对广域的启示：“传片段 + 端点选择性重算”是跨域复用的正解形态。选择器在本地运行、只依赖已缓存的紧凑特征，意味着接收端不必回传任何东西就能决定重算哪几块；重算量被压到 5% 预算，跨域带宽与本地算力的配比因此可调。

3. Selective and Hybrid-State Communication for Latent Multi-Agent Systems

  • 链接：https://arxiv.org/abs/2610.37779
  • 时间：2026-10-27
  • 方向：混合线性注意力 · KV+状态通信 · 多 agent

摘要：多 agent 系统的通信是主要瓶颈；潜在通信通过传内部状态减少自然语言往返，但这些传输仍然昂贵，且通常围绕传统 KV 表示设计。论文从两个角度切入：SelectKV 是边界感知的方法，有选择地传 KV 状态同时保护继承来的上下文；HyLaMAS 把潜在协作扩展到混合线性注意力模型，通过共享工作区同时通信 KV 缓存与循环状态。六个基准确认下，SelectKV 把通信的 KV 位置与逻辑 KV 负载减少 9.7–9.9%，两个基准精度不变、三个在一个百分点内、HumanEval+ 低 6 分；在 Qwen3.5 各规模上，HyLaMAS 相对文本式多 agent 通信把解码输出 token 减少 53–80%，取得 1.16–2.78× 加速。

对广域的启示：这是本专题里唯一明确回答“状态怎么跨 agent 传”的论文——混合模型必须同时传 KV 与循环状态，二者缺一不可。对跨域的直接含义是：传输协议要按模型架构分叉，纯 KV 的通道在混合模型上是不完整的。

4. GaugeRoPE: RoPE-Compatible Executable Latent Attention

  • 链接：https://arxiv.org/abs/2611.20524
  • 时间：2026-11-16
  • 方向：latent 压缩 · RoPE 兼容 · 可直接执行

摘要：latent KV 压缩把历史 K/V 映射到紧凑表示以减少内存，但通用压缩后的 key 状态必须还原到原始维度才能施加 RoPE 并算注意力分数，这给解码路径加上随序列增长的开销。论文刻画了“latent KV 表示何时可以直接作为预训练 RoPE 的执行状态”：对基于 RoPE 的 transformer，旋转 key 路径的精确静态线性执行要求 latent-to-native 映射通过一个 intertwining 关系保持预训练的 RoPE 作用，这把精确混合限制在共享同一 RoPE 频率的坐标上。据此构造的 GaugeRoPE 是训练免的：一个保持旋转作用的 RoPE 兼容载体，加上一个近似位置无关的残差 key-value（RKV）修正来补充 key 与 value 的信息，两者都不需要逐 token 重建稠密历史 K/V。Mistral-7B 上实现 5.85× KV 压缩且质量接近全缓存，解码吞吐最高达未压缩基线的 2.48×。

对广域的启示：“压缩态一路走到计算”有了理论基础——只要满足 RoPE 的 intertwining 条件，接收端不必先解压就能直接跑注意力。这对跨域尤其关键：省下的不只是带宽，还有接收端的解压开销。

5. The State Is Not the Bottleneck: A Paged-State Gated-DeltaNet Tile on a Tri-Mode Multicast Mesh

  • 链接：https://arxiv.org/abs/2611.18422
  • 时间：2026-11-13
  • 方向：递归状态分页 · 状态体积 · 硬件实测

摘要：线性注意力模型用固定大小的递归状态替代增长的 KV。在边缘 FPGA 上这个状态可能超出片上内存、必须分页到外部存储。论文问的是：这种分页会不会主导解码成本？作者做了一个硬件 tile，在 Agilex 5 FPGA 上计算一个自研 3.69 亿参数混合 Gated DeltaNet 模型的完整一层并对递归状态分页。模型状态需要 6.2 MiB，而器件只有 0.87 MiB 块内存；分页每个解码 token 增加 26.0 MB 访存流量，但最多只占计算总量的 11.2%。75 MHz 下（合成权重）这一层一个 token 耗时 11.15 ms，其中权重矩阵向量乘约占 62%，状态阶段（含分页）占 13%。论文还对比了定点与浮点误差，并验证硬件与定点参考逐位一致。

对广域的启示：这是最硬的“状态有多大、搬它多贵”的实测数据：6.2 MiB 的状态、每 token 26 MB 分页流量，只占 11.2%——说明循环状态的搬运成本相对算力是可接受的。把“分页到外部存储”换成“跨网传到对端”，量级上完全可行；这也从硬件侧支持了本期主线：跨域传状态比传整段 KV 划算得多。

二、传输与内存池

6. HyCoInfer: Cloud-Edge Collaborative Inference for Large Language Models on Heterogeneous GPU-FPGA Architectures

  • 链接：https://arxiv.org/abs/2611.22086
  • 时间：2026-11-17
  • 方向：云边协作 · 广域 KV 传输 · 带宽自适应压缩

摘要：LLM 服务主要依赖云 GPU，但自回归解码受限于访存、算术单元常被闲置；边缘 FPGA 解码效率好，却撑不起高并发。HyCoInfer 把 prefill 放在云 GPU、decode 分散到云 GPU 与边缘 FPGA，正面处理三个障碍：异构加速器之间的容量平衡、大 KV cache 跨越受限广域链路、以及异构执行带来的额外时延。它把 FPGA 解码容量纳入 GPU 的 prefill/decode 角色划分，并按队列负载、prompt 长度与网络状态放置请求；技术上组合了逐层流水线传输、解码端预计算、以及基于残差向量量化的带宽自适应 KV 压缩。用两张 V100 与一块 Alveo U280、在 100–1000 Mbps 链路上实测：500 Mbps 时请求 goodput 最高为纯云 vLLM 的 4.11×，平均端到端时延降低最多 61.1%；通信密集任务增益最大，且每请求能耗下降。

对广域的启示：这篇几乎就是“跨广域 KV 传输”的标准答案模板——逐层流水线（边传边算）+ 带宽自适应量化（RVQ）+ 网络状态感知的放置。值得注意的是它在 100–1000 Mbps 这个真实广域/边缘带宽区间做的评估，比动辄 100 Gbps 的集群内论文更有参考价值。

7. XM-Sparse: High-Throughput Sparse-Attention LLM Serving over Scale-up Memory Pools

  • 链接：https://arxiv.org/abs/2611.22280
  • 时间：2026-11-17
  • 方向：稀疏注意力 · scale-up 内存池 · 双缓存卸载

摘要：生产模型越来越多用稀疏注意力做长上下文，但服务系统仍要保留完整 KV 历史，GPU HBM 容量因此成为并发上限。现有系统把 KV 卸载到主机内存，受限于 PCIe 带宽与主机内存容量；新兴的 scale-up 内存池（如 X-Mem）同时缓解两个限制。论文先做深入分析，发现即使有 scale-up 内存池，解码吞吐仍受 HBM 容量约束——因为热 KV 缓冲与常驻的 indexer key（K-index）缓存占用了大量 HBM，且两者访问模式不同。XM-Sparse 是首个面向 scale-up 内存扩展的稀疏注意力卸载系统：把两种缓存都积极卸载，并为各自匹配定制 I/O——动态选取的 KV 条目用 TMA 检索与注意力在 tile 级流水线中融合来隐藏按需检索延迟；可预测的 K-index 访问用 SM 高效的 GPU 发起 DMA 预取页，并与延迟关键操作协调以免干扰解码。在 SGLang 上实现，DeepSeek-V3.2 与 GLM-5.3、16K–1M 上下文下，解码吞吐最高为 PCIe 方案 ECHO 的 4.98×、HiSparse 的 4.52×，比同平台朴素集成高 1.34×。

对广域的启示：热数据与冷数据要用不同的搬运机制——这是跨域设计常被忽视的一点。KV 条目是“按需、难预测”，indexer key 是“可预测、可批量预取”；跨域时前者适合小步快取，后者适合提前批量同步。

8. Storing the Gemma 4 K=V Cache Once: Exact Global-KV Memory Savings in a Paged Serving Engine with Unchanged Attention Kernels

  • 链接：https://arxiv.org/abs/2611.23035
  • 时间：2026-11-17
  • 方向：架构感知存储 · 精确共享 · 传输/卸载

摘要：Gemma 4 31B 的全局注意力层里，value 就是归一化后的 key 投影，key 则是 value 乘一个固定权重，并只对四分之一维度做 RoPE。Gemma 4 报告称该设计能把全局 KV 缓存减少最多 37.5%，但作者检查的开源服务引擎仍在存一份完整 key 和一份完整 value（每 KV 头每 token 1024 个 value）。论文改成只存一行 640 个 value，在实数算术下精确，且不修改 paged attention kernel——让 kernel 通过两个重叠的 strided view 把它分别读作 key 缓存与 value 缓存。vLLM 原型（16-bit 31B）上输出与在标准缓存上模拟同一算术的结果逐位一致，432 个最终答案中 2 个与标准引擎不同（在其运行波动内），稳态解码每请求 KV 内存降 1.34–1.40×（32K–64K token）；在两块 A100 的 prefill/decode 组合、NIXL 传输 + CPU offload 下，15 GiB 池的解码引擎每步 token 数是标准引擎的 1.38×（16K prompt）、1.24×（8K prompt），block pool 模型预测误差在 1% 内。代价是等 batch 下 eager step 慢 4%–9%，且暂不能与 8-bit KV 缓存默认叠加。

对广域的启示：架构自带的冗余是免费午餐——不需要任何近似，就能把跨域传输的 KV 字节降 1.34–1.40×。这类“按模型结构精确去重”应当排在量化之前：它不引入误差，也不会和解压路径打架。

三、评估与状态通信

9. Cross-Modal StateKV Injection for Communication in Multi-LLM Systems across Temporal Segments

  • 链接：https://arxiv.org/abs/2611.22304
  • 时间：2026-11-17
  • 方向：跨模型状态注入 · 视觉 KV · 多 LLM 通信

摘要：多模态多模型视频理解需要一个能传递互补视觉观察的通信接口。文本通信可解释，但引入中间生成阶段并可能丢失后续推理所需信息。论文研究 Cross-Modal StateKV Injection：一个 provider–carrier 框架，在视觉 token 位置通过 KV 状态通信。provider 模型观察互补的视频帧，其视觉 KV 状态被对齐并投影到 carrier 的表示空间，通过门控残差更新整合进 carrier。注入保持 carrier 的 KV 缓存序列长度不变，但保留 provider 与通信模块所需的额外计算。在 MLVU 与 Video-MME 上，用两种 provider 架构比较 carrier-only 推理、文本通信与 StateKV：结果显示温和且依赖任务的精度增益，以及比文本通信基线更低的报告延迟，部分类别无变化。

对广域的启示：这是一次诚实的“负结果倾向”报告——直接注入别人的 KV 状态收益有限，且强依赖任务类别。它从侧面印证了本期主线：跨模型/跨域的状态复用不是“插进去就行”，需要任务条件化的适配层（如 LatentRemedy 的做法）。

10. Re-Reading Is Not Free: Token Traces and Cache-Aware Energy Estimation for LLM Agents in Software Engineering

  • 链接：https://arxiv.org/abs/2611.20873
  • 时间：2026-11-16
  • 方向：能耗核算 · 缓存读取占比 · Agent 负载

摘要：LLM 从对话助手变成嵌入软件开发流程的自主 agent 后，估算其环境足迹不能再用传统 token 统计。现有能耗估算器只看孤立的请求-响应交互，忽略了累积上下文的重复处理、缓存复用与委派给子 agent 的工作。论文分析了十周真实 AI 辅助软件开发中 42 个会话、752 个任务片段、近十亿 token：缓存上下文读取占所有 API 上报 token 的 94.8%，而未缓存输入只占 0.017%；每生成一个 token 约读取 260 个缓存 token。上下文在一个会话内增长 5.3 倍（单个任务内 1.4 倍）。作者把分析式推理能耗模型扩展到能计入缓存上下文处理，得到 cache-aware 混合估算器：该负载约 250 kWh，而输出导向的 EcoLogits 只估约 10 kWh，25 倍差距主要来自缓存读取。从全新上下文开始每个任务可把估算降低约 60%；父会话日志只记录子 agent 最后一次内部调用，使委派 token 被少算 10 倍。

对广域的启示：缓存读取已经是推理的主导开销（94.8%）——这彻底改变了跨域系统的优化目标：与其纠结“传 KV 还是重算”，不如问“这份缓存到底被读了多少次”。读取次数高的前缀值得跨域复制多份，只读一次的完全不值得传。

今日观察

  1. 非前缀复用的核心矛盾被正面命名：LatentRemedy 给出量化——冲突任务下直接复用掉 90%，说明“搬过来的 KV”并不等于“可用的 KV”，这与之前收录的 Close Enough is Nowhere Near 完全一致。
  2. 补救信息可以极小：LatentRemedy 用几个 latent token、CacheWeave 用 5% 重算预算——跨域复用的最优形态可能是“传主体 + 传少量校准信号”，而不是全量搬运。
  3. 状态搬运的成本有了实测数字：Paged-State GDN 给出 6.2 MiB 状态、每 token 26 MB 分页流量、只占 11.2%——从硬件侧支持“传状态比传 KV 划算”。
  4. 压缩正在从“近似”走向“精确 + 可执行”：Gemma 4 的 K=V 单份存储是零误差的 1.34–1.40×，GaugeRoPE 让压缩态可直接执行（5.85×）。这两条路线对跨域最有价值，因为它们不牺牲质量也不增加接收端解压成本。
